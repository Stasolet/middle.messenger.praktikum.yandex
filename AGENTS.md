# AGENTS.md

Учебный проект — мессенджер (Яндекс практиikum, middle). Не production: приоритет — понятная архитектура, а не оптимизации.

## Стек

TypeScript + Vite (MPA: несколько `.html`-точек входа в `vite.config.js`) + Handlebars + SCSS. Фреймворка нет.

## Архитектура

Feature-Sliced Design: `src/shared` → `src/entities` → `src/features` → `src/widgets` → `src/pages`. Импорт только снизу вверх; внутри слайса — через barrel `index.ts`.
Данные: `mocks/*.json` → `shared/api` (transport, единственное место импорта JSON) → `entities/*/model/*-service` (домен) → страницы (composition root).

## Рендеринг

- Шаблон компонента — `.hbs`-файл, импортируется как строка (vite-плагин `vite-plugin-hbs-raw`), компилируется Handlebars при каждом `render()`.
- Все компоненты наследуют `BaseBlock` (`src/shared/ui/base/base.ts`):
  - `element()` — получить/отрендерить корневой DOM-элемент; `setProps()` — partial-merge props + **полный ре-рендер**;
  - `this.refs` — элементы по атрибуту `ref="name"` в шаблоне (атрибут снимается после сбора);
  - `this.events` — карта `{ eventName: handler }`, вешается на **корень** компонента (невсплывающие события, напр. `blur`, слушать только на самом элементе-цели);
  - `componentDidMount` / `componentWillUnmount` — хуки.

## Дочерние компоненты

Регистрируются один раз: `registerComponent(X)` (см. `initHbs()` в `src/shared/lib/initHbs.ts`, вызывается во входах страниц). В шаблонах: `{{{X prop=value ref="name"}}}`.
Helper кладёт в props родителя: `__children` (embed в шаблон), а при наличии `ref` — `__namedChildren[name]` = **инстанс** ребёнка и `__refs[name]` = его DOM-элемент. Это канал связи родитель↔ребёнок для точечного доступа. Для перечисления детей use `this.children` (все, без ref) + type guard, напр. `isFormField`; в `namedChildren` поле без `ref` не попадёт — не полагаться на него как на реестр.

## Документация по областям — обязательно к прочтению

Прежде чем править соответствующий код, открыть док через Read и считать его обязательной инструкцией:

- UI-компоненты (`Input`, `FormField`, отрисовка ошибок) → `docs/components.md` — при работе с `src/shared/ui` и компонентами на страницах.
- Формы (blur/submit-валидация, submit-поток, сбор значений) → `docs/forms.md` — при работе с `src/widgets/form`, `src/shared/lib/validations.ts`, login/signin/profile.

## Важные грабли

- `setProps()` пересоздаёт DOM **и дочерние инстансы**: теряет фокус, каретку, value и связи `onBlur`-колбэков. Для частых UI-обновлений (ошибок валидации) менять DOM императивно через refs.
- Роутера нет: навигация ссылками / `window.location`.
- Глобальные SCSS-переменные (`src/styles/global.scss`) инжектятся vite автоматически, `@use` в файлах не нужен.
- Новое поле в props компонента — сначала спроси себя: не `BaseBlock` ли его место; и если кажется что `BaseBlock` — ещё раз: не оверинжиниринг ли это, согласовать с пользователем.
- Комментарии описывают код, а не правку: не оставлять следы рефакторинга («раньше было X», «не Y, потому что…») и не дублировать то, что видно из кода.

## Как поддерживать этот файл

- Источник контекста для агентов: устаревшая строка хуже отсутствующей.
- Описывать только то, что не выводится из кода: зачем, инварианты, соглашения, грабли. Механику кода не пересказывать.
- Нетто-рост: сначала сократить, слить или удалить устаревшее, потом добавлять; ориентир — 80 строк.
- Фактические правки (изменились путь/имя/объём — обновить затронутые строки в том же изменении) агент вносит сам.
  Сущностные (новое правило или конвенция, удаление раздела) — предлагать diff'ом и применять после согласия.
- Домены живут в `docs/<домен>.md`, этот файл — индекс + общепроектное. Факт хранится ровно в одном месте, не дублировать root и док.
  Правила правок те же; создание нового дока — сущностное, предлагать.
- Замеченное расхождение, в котором агент не уверен, — озвучить вопросом либо пометить строку `<!-- stale? -->`; молчать нельзя.
